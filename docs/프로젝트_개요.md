# 프로젝트 개요 — 기가(GW) 막힐 땐: AI 데이터센터 전력 수요 예측 서비스

> 이 문서는 구현 전에 전체 윤곽을 확인하기 위한 개요다. 코드는 포함하지 않는다.
> 기준 자료: 팀 기획서, `팀플/` 폴더의 `hourly_clean.csv` · `README.md` · `temp.html`, 실습 `project/` 폴더

---

## 1. 한 줄 요약

실습 `project/`(HAIC 주가 예측 서빙·MLOps·AIOps 파이프라인)의 **폴더 구조와 파일을 그대로 가져와**, 예측 대상만 "다음날 종가"에서 **"데이터센터의 다음 1시간 전력 사용량"** 으로 바꾼다. 화면은 `temp.html`(실습 정답지 대시보드)의 기능을 바탕으로, 패널 배치를 파이프라인 중심으로 재구성하고 디자인을 새로 입힌다. 정답지 화면에만 있는 기능은 팀이 항목별로 구현 여부를 정한 뒤(9-1), 고른 항목만 정답지 방식으로 백엔드와 화면에 추가한다(B안).

## 2. 진행 원칙

1. **틀은 그대로:** `project/`의 폴더 구조, 파일 구성, 처리 흐름(업로드 → baseline 학습 → MLflow 게이트·승격 → FastAPI 서빙 → 드리프트 감지 → fine-tuning 재학습 → 재배포)을 그대로 쓴다.
2. **바꾸는 것은 이름과 값:** 엔드포인트의 요청·응답 필드명, 변수명, CSV 컬럼명, 상수값(입력 길이, 게이트·드리프트 기준)이 주된 변경 대상이다.
3. **예외 — 정답지 기능의 선택 구현 (B안):** `temp.html`(완성본)에는 있지만 `project/`에는 없는 기능은 **9-1 체크리스트에서 팀이 항목별로 구현 여부를 모두 정한 뒤** 개발에 착수한다. 구현하기로 한 항목만 `temp.html`의 코드를 기준으로 새로 작성하고, 기존 파일의 흐름은 건드리지 않는 **덧붙이는 방식**으로만 추가한다 (7-2).
4. **개발 착수 조건:** 9-1 체크리스트가 전부 확정되기 전에는 코드를 작성하지 않는다.
5. **담당:** 프론트엔드와 백엔드를 한 사람이 모두 맡는다. 새 코드는 고른 항목에 해당하는 부분만 백엔드·프론트엔드에 각각 추가한다.
6. **화면:** `temp.html`의 기능을 바탕으로 패널 배치를 재구성하고(8-2), 디자인은 관제 시스템 운영 센터 컨셉으로 새로 만든다 (8-4).
7. **청중은 경영진:** 기술 내용은 쉽게 설명하고, 화면과 발표는 "어떤 가치를 주는가" 중심으로 구성한다.

## 4. 데이터

### 4-1. 출처와 형식

- **출처:** NREL ESIF(Energy Systems Integration Facility) HPC 데이터센터의 PUE 공개 데이터 (README 참고). AI 전용이 아닌 **HPC 데이터센터 실측 데이터**라는 점을 발표에서 밝힌다.
- **정제 파일:** `hourly_clean.csv`, 1시간 간격

| 컬럼 | 의미 | 범위 (결측 제외) |
| --- | --- | --- |
| `date_utc`, `time_utc` | UTC 날짜·시각 | 2015-11-10 03:00 ~ 2025-08-29 18:00 |
| `energy_kwh` | 1시간 전력 사용량(kWh) = 그 시간의 평균 전력(kW) | 140 ~ 4,158 (평균 1,580, 중앙값 1,235) |
| `humi_pct` | 외기 상대습도(%) | 9 ~ 100 |
| `temp_F` | 외기 온도(°F) | −11 ~ 103 |

### 4-2. 데이터를 살펴보고 확인한 사실

| 확인한 사실 | 수치 | 프로젝트에 미치는 영향 |
| --- | --- | --- |
| **결측이 많다** | 전체 85,936행 중 유효 71,372행(83%). 2015년 0%, 2016년 54%, 2021년 67%만 채워짐. 가장 긴 무결측 구간은 2024-11-05 ~ 2025-02-04(2,179시간, 약 91일) | 실습 코드는 행을 순서대로 이어 붙여 입력 시퀀스를 만든다. 결측 행을 그냥 지우면 서로 떨어진 시각이 한 시퀀스에 섞인다. **연속 구간만 쓸지, 짧은 결측을 보간할지** 정해야 한다 |
| **연도별 사용량이 계단식으로 늘었다** | 연평균 2016년 866 → 2022년 1,261 → **2023년 2,175 → 2024년 2,922** kWh | 장비 증설 같은 **실제 드리프트**가 데이터에 들어 있다. 2022년 데이터로 학습한 모델에 2023년 이후를 넣으면 인위적인 조작 없이 드리프트 감지 → 재학습을 시연할 수 있다 |
| **평일/주말 차이가 거의 없다** | 평균 1,576(평일) vs 1,590(주말) kWh. 시간대별로도 거의 평평 | HPC 센터는 24시간 일정하게 가동된다. 기획서의 "평일 낮 vs 주말 낮 패턴 차이"는 이 데이터로는 뒷받침되지 않는다. **입력 길이를 168(1주)로 할 근거가 약하다** |
| **기온·습도와 전력 사용량의 상관이 거의 없다** | 상관계수 0.01 / −0.01 | 정제 파일에는 냉각 전력이 따로 없고 합계만 있어서일 수 있다. 기온을 입력 피처로 넣어도 정확도 개선은 작을 수 있다 |
| **README와 정제 파일의 컬럼이 다르다** | README에는 `it_power_kw`, `cooling_kw`, `hvac_kw`, `pump_kw`, `plug_and_light_kw`, `pue`가 있지만 정제 파일에는 `energy_kwh` 하나뿐 | 기획서의 "주요 입력" 목록(IT·냉각·공조·펌프·조명 전력, PUE)은 정제 파일로는 쓸 수 없다. `energy_kwh`가 정확히 무엇의 합계인지 정제 담당자에게 확인이 필요하다 |

## 5. 모델 설계 (실습 대비 변경점)

| 항목 | 실습 (HAIC) | 이번 프로젝트 | 비고 |
| --- | --- | --- | --- |
| 예측 대상 | 다음날 종가($) | **다음 1시간 전력 사용량(kWh)** | |
| 입력 피처 | 2개 (종가, 거래량) | **팀 논의 예정** | 고려 사항: 피처 2개(예: 전력 사용량 + 외기 온도)면 스케일러·모델 구조를 그대로 쓸 수 있다. 습도까지 3개로 늘리면 스케일러와 모델 입력 크기를 함께 바꿔야 한다 |
| 입력 길이 | 20 | **팀 논의 예정** (후보: 24 / 168) | 고려 사항: 기획서 안에서도 24와 168이 섞여 있다. 168은 1주 패턴을 볼 수 있지만, 이 데이터는 평일/주말 차이가 작고(4-2) 결측이 많아 168개가 끊김 없이 이어진 구간이 더 적다. 길이가 정해지면 판정 윈도우·재학습 행 수·시뮬레이션 배치 길이·화면 상수가 함께 정해진다 |
| 정규화 | 종가·거래량 min-max, 1회 fit 후 고정 | 전력·기온 min-max, 1회 fit 후 고정 | 사용량이 해마다 커지므로, 학습 구간의 최댓값을 넘는 값이 들어올 수 있다는 점에 유의 |
| 모델 | 3층 LSTM | 그대로 | |
| 재학습 | 최근 (21 + 입력 길이)행, warm start 10 epoch | 최근 (판정 윈도우 + 입력 길이)행, warm start | 실습 코드에 숫자 21이 직접 적힌 곳이 있어 함께 바꿔야 한다 |

## 6. 운영 설계 (기획서 기준, 수치 재검토 필요)

| 항목 | 기획서 | 데이터로 확인한 점 · 제안 |
| --- | --- | --- |
| 배포 게이트 | 검증 RMSE ≤ 3MW | **3MW는 평균 사용량(약 1.6MW)보다 커서 의미가 없다.** baseline을 먼저 학습해 보고 kW 단위로 다시 정한다. 실습 `RMSE_GATE` 상수 하나로 구현된다 |
| MAPE | 10% 이하 | 최솟값이 140kWh라 0으로 나뉘는 문제가 없어 사용 가능하다. 단, 실습 코드에는 MAPE 계산이 없으므로 게이트에 넣으려면 추가가 필요하다 |
| Peak Recall | 90% 이상 | 실습 코드에 없는 지표다. 게이트로 쓸지, 발표용 평가 지표로만 쓸지 정해야 한다 |
| 피크 경보 기준 | 계약전력의 90% | 이 데이터에는 계약전력 정보가 없다. 대안: 학습 구간 사용량의 상위 10% 값(전체 기준 2,904kWh)을 기준선으로 사용. 사용량이 해마다 늘어나므로 최근 구간 기준으로 정하는 것이 좋다 |
| 드리프트 판정 | 최근 24건 RMSE > 기준값 (기획서 3-3) / MAPE 30% 악화 2회 연속 (기획서 3-1 하단) | 두 방식이 섞여 있다. 실습 구조를 그대로 쓰려면 **최근 24건 RMSE 방식**이 맞다 |
| 예측 응답시간 | 5초 이내 | 실습에서 `/predict`는 0.016초였으므로 여유 있게 만족한다 |

### 7-2. 추가 후보 파일 (B안: 실습 정답지 방식, 9-1에서 항목별 확정)

아래는 정답지에 있는 파일 전체다. 9-1에서 **구현으로 정한 항목에 필요한 파일만** 만든다.

| 추가 위치 | 역할 | 이 기능이 공급하는 화면 |
| --- | --- | --- |
| `serving_app/monitoring/logger.py` | 요청마다 경로·상태코드·응답시간을 `requests.log`에 기록하는 미들웨어 | 운영 지표 요약 (요청 수·응답시간·성공률) |
| `serving_app/routers/system.py` | `/system/info`, `/system/timeseries`, `/system/alerts`, `/system/dataset` | 시스템 설정, 운영 지표 요약, 최근 알람, 데이터셋 정보 |
| `serving_app/routers/models.py` | `/models/current`, `/models/history` (MLflow 레지스트리 조회) | 현재 운영 모델, 재학습 이력, RMSE 추이 |
| `serving_app/routers/metrics.py` | `/metrics/summary` (요청 로그 전체 요약) | 지표 요약 |

- 기존 파이프라인(`predict`, `monitoring/`, `train_and_register.py`)의 동작은 바꾸지 않는다. 새 파일은 **기존 로그와 MLflow 기록을 읽어서 보여주기만** 한다.
- `/system/alerts`는 기존 `aiops` 로거가 남기는 `[WARN]/[INFO]/[OK]` 기록을 그대로 모아 보여준다.
- `/models/*`는 레지스트리 모델명(`MODEL_NAME`)을 바꾸면 그 이름으로 조회해야 한다.
- 실습에서 확인한 레지스트리 문제(승격 시 이전 버전이 모두 Production으로 남음)가 "재학습 이력"과 "현재 운영 모델" 표시에 그대로 드러나므로, 표시 기준(가장 최근 Production 버전)을 정해 둔다.

| GET | `/system/dataset` | 학습 데이터셋 통계 | 행 수, 시작·종료 시각, 최소·최대 | `min_close, max_close, mean_volume` → 사용량·기온 통계 |

| GET | `/models/history` | 등록 버전 이력 | 버전별 `rmse`, `mode`, `stage`, 등록 시각 | 없음 |
| GET | `/metrics/summary` | 전체 요청 지표 요약 | `avg_latency_ms`, `error_rate`, `request_count` | 없음 |

- 기획서 API 표의 예시 필드명(`datetime`, `it_power_kw`, `predicted_elect`)은 정제 데이터 컬럼과 맞지 않는다. **데이터 컬럼과 같은 이름으로 통일**할 것을 제안한다.
- 핵심 기능 ② 피크 경보를 응답에 넣으려면 `/predict` 응답에 경보 여부 필드 하나를 추가한다.

## 8. 프론트엔드 (`temp.html` → `serving_app/static/index.html`)

### 8-1. 출발점

- `temp.html`은 실습 정답지 데모의 4탭 대시보드(Dashboard / Simulation / Datasets / System)다.
- 정답지 API(7-2)를 추가한 패널만 동작한다. 추가하지 않기로 한 패널은 기존 API로 대체하거나 화면에서 뺀다 (9-1의 "대체 수단" 열).
- 단, `temp.html`에는 **CSV 업로드 화면이 없다.** 데이터 공급에 필요하므로 실습 대시보드의 업로드 카드를 옮겨온다.

### 8-2. 레이아웃 재구성 (팀 제안)

**현재 Dashboard 탭의 "드리프트 감지 기반 재학습 파이프라인" 자리를 중심 영역으로 키우고, 흩어진 패널을 그 안으로 모은다.**

| 옮길 패널 | 지금 위치 | 새 위치 |
| --- | --- | --- |
| 운영 지표 요약 (요청 수·응답시간·성공률·RMSE·드리프트 점수) | Dashboard 상단 | 파이프라인 중심 영역 |
| 최근 알람 | Dashboard 오른쪽 | 파이프라인 중심 영역 |
| 현재 운영 모델 | Dashboard 오른쪽 | 파이프라인 중심 영역 |
| 예측 실행 | Simulation 탭 | 파이프라인 중심 영역 |
| 정상·드리프트 배치 전송 | Simulation 탭 | 파이프라인 중심 영역 |

**재구성 후 정해야 할 것**

| 항목 | 선택지 |
| --- | --- |

### 8-3. 디자인과 내용 변경

- **디자인 (CSS·레이아웃): 대폭 변경** → 8-4 디자인 컨셉 적용
- **문구:** 종가·거래량·$ → 전력 사용량·kWh(MW), "Day1/Day3"·"TODO 체크용" 같은 실습 표현 제거, HAIC 표기 → 서비스명
- **화면 상수:** 입력 길이 20 → 결정값, 판정 윈도우 21 → 결정값 (5번 입력 길이 논의 후)
- **드리프트 시뮬레이션 배치:** 지금은 주가처럼 무작위로 움직이는 값(랜덤워크)을 만들어 보낸다. 전력 데이터에 그대로 쓰면 정상 배치도 드리프트로 잡힐 수 있다. **정상 배치 = 실제 데이터의 기존 구간, 드리프트 배치 = 사용량이 뛴 2023년 이후 구간**을 보내는 방식을 제안한다
- **경영진용 표현:** 지표 이름을 쉬운 말로 바꾸고(예: RMSE → "평균 예측 오차(kW)"), 피크 경보를 눈에 띄게 표시

### 8-4. 디자인 컨셉 — 관제 시스템 운영 센터

**방향:** 회색 배경의 관제실 화면. 문구는 딱딱하고 직관적으로 쓴다. 장식보다 상태를 빠르게 읽는 것이 우선이다.

**컬러 팔레트와 역할 (제안)**
